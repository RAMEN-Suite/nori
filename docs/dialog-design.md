# Dialog design

- Write dialog titles as short, clear statements or questions that describe their purpose. Use sentence case and specific actions or affected items; avoid vague titles such as “Warning” or “Are you sure?”. Titles and action labels should make the decision understandable together.
- Use the shared Sushi dialog host for focus management, Escape, pending state and errors. Use public component APIs and tokens.
- Centre dialogs. Use the compact width (24rem) for confirmations and 28rem for validation and short choices, the form width (36rem) for editing, and 42rem for Settings with its Sushi navigation. Always respect the viewport.
- Use the shared `styles/_surface-list.scss` mixins for comparable dialog lists: 0.375rem frame padding, 0.125rem content inset, 0.375rem/0.5rem row padding, 0.625rem content gap and 2.75rem minimum row height. Compose these with Sushi List size xs so wrapper spacing stays consistent.
- Keep the title, introductory text and bottom actions fixed; scroll only the middle content. Leave space for focus rings and use thin scrollbars near the right edge without moving the content towards them.
- Use consistent spacing, the shared dialog radius and border, and no shadow or glow. Keep labels above full-width controls.
- Put actions at the bottom right: neutral Cancel first, one primary action last. Destructive actions use the error colour and a specific verb. Avoid vague OK/Yes/No and unnecessary footers.
- Use Sushi button size `sm` consistently for dialog actions. Hide consequence actions with zero affected entries, including their empty wrapper.
- Every labelled dialog action starts with a matching Lucide icon (1rem, aria-hidden): X for Cancel/Close, Save for saving, Plus for adding, Eraser for removal, and RotateCcw for reset. Keep icon placement and spacing consistent; titles remain plain.
- Base Nodes categories show levels as “number – model name”. Confirmation detail rows for model levels show only the name, followed by their own node and relation counts. Model levels keep their plain number column. Do not add level numbers to Refinement categories or Inspector source labels. Item counts remain soft badges.
- Settings and node colours may close on backdrop click because changes apply immediately. Keep confirmation and editing dialogs protected from backdrop dismissal, especially while an action is pending.
- Colours, appearance and shortcuts apply immediately. Provide contextual reset actions at the bottom right, without Save or Cancel. Give equally weighted colour actions the same soft neutral style.
- Emphasize affected names in confirmation messages with semibold text instead of quotation marks. Pass translated message keys and named parameters to the shared confirmation content; never interpolate HTML.
- Project deletion on Open project uses a simple confirmation that explains permanent removal of the entire project and suggests opening/exporting it for a backup. Do not enumerate affected nodes, relations or levels there.
- For individual node or relationship deletion, omit the selected declaration from consequence lists and counts; match both model and element IDs so dependent declarations on other levels remain visible.
- Show deletion consequences as full-width clickable statements giving the affected node/relation counts and, for model-level deletion, the number of additional dependent levels. Exclude the selected model level from that level count and list; selecting the level statement shows the dependent levels by name with their own node and relation counts, with the same inspect-and-resume flow as nodes and relations. Selecting one slides the confirmation left and reveals a separate detail surface on the right within the same modal focus scope. Use a single scrollable Sushi List with compact, non-interactive model-level headings and divider lines. Avoid nested cards. Under affected node names, show small counts of incident relationships, own properties and own constraints (including property constraints). A jump action pauses the confirmation and opens the normal workspace at the affected node. A persistent action notification above the version footer restores the original route, selected consequence list and scroll position. Give it a task icon, calm title and hint, neutral outlined Resume action and Cancel icon. Viewing, selection and navigation keep the action available. A change to the project model cancels it; viewport and colour preferences do not. Recheck model revisions before resuming. Do not add a separate graph preview. Let the left dialog determine the height of both surfaces; keep the right surface slightly narrower and scroll its list within that height. Each affected-item row is a single navigation button with a leading node, relationship or model-level icon. Use short statement labels with a leading magnifying-glass icon, without repeating the removal consequence. Keep endpoint names prominent and relationship names secondary. Escape closes the details first and returns focus to the triggering action. Stack the details on narrow viewports and respect reduced motion.
- Confirmations explain the consequence and whether it is reversible, using shared confirmation content without an additional warning/info box. Do not add decorative icons to confirmations. Keep validation errors inline, accessible, and near their context.
- Show introductory guidance as calm, naturally wrapping text rather than decorative message boxes. Reserve message boxes for feedback. Group shortcuts under translated headings with Lucide icons and make scrolling apparent when content actually overflows.
- Edit within the existing dialog rather than opening nested dialogs. Translate all visible text into every registered language.
- Use the node-colours dialog as the visual reference: a plain title without an icon or forced uppercase, calm introductory text, a thin bordered content area, and compact buttons at the bottom right. Editing forms use neutral text Cancel and primary Save; immediately applied settings use equally weighted soft actions.
- All dialogs share the same opening animation: gentle fade with 6px upward movement over 280ms, easing out; closing uses a short 180ms fade. Configure this centrally in the dialog host. Respect reduced motion and Nori’s animation preference.

Reference: [Material dialog guidelines](https://m1.material.io/components/dialogs.html).

## Open Sushi issue

- Dialogs lock their position when opened. Switching from a short property list to a taller editing form grows the dialog downwards rather than keeping it centred. Offer automatic recentering on content resize (while preserving deliberate dragging), or a public reposition method. Reproduce with Edit annotations → Add annotation type. Avoid compensating through private dialog styles or forced reopening.

- Sushi accordion focus outlines extend outside a clipped collapse container; the catalogue currently uses the public focus-offset token to draw them inside. Verify trigger and first/last item focus in expanded and collapsed states. Sushi should provide an inset focus option by default for clipped containers.
- Sushi tab panels currently rely on browser-default focus outlines without a panel focus token. Nori styles the public tabpanel role within Settings; Sushi should expose consistent panel focus tokens.
